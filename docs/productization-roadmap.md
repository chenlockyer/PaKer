# 《纸牌建筑师》完整产品化路线

> 文档状态：产品与技术执行规划  
> 适用阶段：从浏览器技术原型到可在 Steam 销售的正式 PC 游戏  
> 当前技术栈：Vite、React、Three.js、React Three Fiber、Cannon  
> 推荐首发平台：Windows / Steam  
> 推荐商业模式：买断制主体 + 纯外观 DLC + 大型内容扩展  
> 核心原则：先验证玩法，再完善产品；先做最小桌面化排雷，再建设可信联机

---

## 1. 产品化目标

产品化不是简单地把网页打包成 `.exe`，而是让玩家获得一套可信、稳定、完整且愿意付费的游戏体验。

最终产品应满足以下条件：

1. 玩家通过 Steam 安装、启动、更新和卸载游戏。
2. 启动后直接进入独立全屏游戏窗口，不需要浏览器和命令行。
3. 游戏具备完整菜单、设置、存档、教程、关卡和对局结算。
4. 核心建造、发射和物理坍塌体验稳定且具有重复游玩价值。
5. 本地模式在断网状态下仍能正常运行。
6. 在线模式使用可信身份与权威服务器，客户端不能自行决定胜负。
7. 客户端不包含 API 密钥、服务器私钥或其他敏感信息。
8. 游戏具备性能分级、错误记录、恢复机制和基本兼容性保障。
9. 商业化不破坏物理竞技的公平性。
10. 项目具备持续更新、扩展内容和社区传播的基础。

## 2. 当前项目判断

### 2.1 已有优势

- 已经具备可运行的 3D 建造原型。
- 已经形成较完整的纸牌放置和旋转操作。
- 已经加入风力、坠物、结构稳定性等物理挑战。
- 已有挑战模式、自由建造和多套视觉主题。
- 当前性能可以达到约 50～60 FPS。
- 已形成独特的 1v1 纸牌建筑对战设计。
- 核心概念容易通过短视频展示。

### 2.2 主要缺口

- 当前通过 Vite 开发服务器或 Preview 服务器运行。
- 没有独立桌面程序和正式安装包。
- 没有 Steamworks 接入。
- 没有统一的本地存档目录和版本迁移。
- 没有账号、房间、匹配和游戏服务器。
- 游戏规则与物理结果完全由客户端控制。
- 没有联机反作弊和异常检测。
- 没有崩溃日志、遥测和问题恢复能力。
- 缺少可直接销售的完整内容量。
- 当前 Gemini API Key 存在进入前端构建产物的风险。

### 2.3 总体策略

不立即迁移 Unity 或 Godot，也不立即建设大型联机后台。

采用以下顺序：

> 最小桌面化验证 → 核心对战垂直切片 → Demo 产品化 → Steam 接入 → 好友联机 → 权威竞技 → 抢先体验 → 1.0 正式版

## 3. 产品结构

### 3.1 核心模式

#### 建造模式

- 自由建造。
- 教学关卡。
- 结构挑战。
- 风力测试。
- 坠物冲击测试。
- 限牌、限高、限时挑战。
- 建筑蓝图保存和分享。

#### 对战模式

- 玩家对 AI。
- 本地双人。
- Steam 好友对战。
- 休闲在线匹配。
- 排位竞技。
- 自定义房间。
- 观战和回放。

### 3.2 对战核心循环

> 选择流派 → 分配纸牌 → 建造防御与发射结构 → 装填 → 瞄准蓄力 → 发射 → 物理破坏 → 抢修或重建 → 击毁目标 → 结算

首个对战垂直切片只实现：

- 一张竞技场；
- 炮台和弩两种流派；
- 一套牌数规则；
- 一个胜负目标；
- 本地玩家对 AI；
- 一局 6～10 分钟的完整循环。

四种流派不必同时进入第一版测试。先让两个流派达到足够成熟的手感，再扩展飞镖和投手。

## 4. 客户端桌面化方案

### 4.1 技术选择

当前阶段推荐使用 Electron 封装现有 Web 技术栈。

选择理由：

- 最大程度复用现有 React 和 Three.js 代码。
- 使用固定版本 Chromium，降低不同系统浏览器造成的差异。
- WebGL、输入和音频行为更容易统一。
- Windows 打包与调试成本相对可控。
- 可以逐步接入 Steamworks、本地文件和系统功能。

当前阶段不优先使用 Tauri，原因是系统 WebView 版本差异可能增加 3D 渲染兼容性测试成本。未来如安装体积和内存成为主要问题，再进行专项评估。

### 4.2 Electron 最小验证范围

第一轮桌面化只实现：

- Electron 主进程。
- 安全的 preload 桥接层。
- 加载 Vite 生产构建。
- Windows 独立窗口。
- 窗口化、无边框和全屏切换。
- 最小化、退出和异常退出处理。
- 正确加载模型、纹理、字体和音频。
- Windows `.exe` 与测试安装包。
- 开发版和正式版环境分离。
- 确认 30 分钟持续运行不出现严重内存增长。

第一轮暂不实现：

- 自动更新。
- 正式代码签名。
- Steam 成就。
- 云存档。
- 好友邀请。
- DLC。
- VAC。
- 完整安装器美化。

### 4.3 Electron 安全基线

- `nodeIntegration` 必须关闭。
- `contextIsolation` 必须开启。
- Renderer 沙箱必须开启。
- 只允许加载本地游戏内容。
- 设置严格的 Content Security Policy。
- Renderer 不得直接访问任意本地文件。
- preload 只暴露经过白名单限制的方法。
- 禁止通过字符串执行任意系统命令。
- 正式版默认关闭开发者工具入口。
- 所有外部链接通过系统浏览器打开。
- 不在客户端保存服务器密钥。

### 4.4 源码与资源保护

客户端代码无法做到绝对保密。产品化目标是提高复制成本，而不是假设客户端不可逆向。

基础措施：

- 正式构建压缩代码。
- 不公开生产版 Source Map。
- 使用 ASAR 封装桌面资源。
- 删除开发日志、测试入口和调试参数。
- 对关键但非敏感逻辑适度混淆。
- 对重要资源建立完整性清单。
- 安装包和可执行文件使用代码签名。

不能依赖的措施：

- 仅通过混淆保护付费数据。
- 把 API Key 写入环境变量后交给 Vite 构建。
- 在客户端判断玩家是否拥有 DLC。
- 在客户端保存排位分数和胜负记录。
- 认为 `.exe` 或 ASAR 代表源码不可提取。

## 5. 密钥与后端安全

### 5.1 当前紧急事项

当前 `vite.config.ts` 会把 `GEMINI_API_KEY` 替换进前端代码。处理要求：

1. 移除客户端对 Gemini 的直接调用。
2. 如果密钥进入过任何公开构建，立即轮换。
3. 建筑提示优先改成内置本地提示库。
4. 如果未来仍需要 AI 功能，只允许客户端请求自有后端。
5. 后端负责鉴权、限流、配额和内容缓存。

### 5.2 永远不能进入客户端的内容

- Steam Publisher Web API Key。
- 数据库密码。
- 云服务管理密钥。
- 支付签名私钥。
- 管理后台令牌。
- 服务器管理权限。
- DLC 和库存签发密钥。
- 反作弊检测规则的完整服务端实现。

## 6. 本地游戏基础设施

### 6.1 存档体系

存档至少分为：

- 玩家设置。
- 教程进度。
- 关卡进度和评分。
- 自由建造蓝图。
- 本地录像。
- 操作预设和键位。
- 无障碍设置。

存档要求：

- 使用系统用户数据目录，不写入安装目录。
- 存档包含版本号。
- 提供旧版本迁移函数。
- 关键写入使用临时文件和原子替换，避免断电损坏。
- 保留一个最近成功备份。
- Steam 云存档只同步必要文件。
- 蓝图和设置分开保存，避免单个文件损坏全部内容。

### 6.2 设置体系

正式版本至少具备：

- 分辨率。
- 全屏、无边框和窗口模式。
- 垂直同步。
- 帧率上限。
- 渲染分辨率或像素比。
- 阴影质量。
- 抗锯齿。
- 环境特效质量。
- 主音量、音乐、音效和 UI 音量。
- 鼠标灵敏度。
- 键位重绑定。
- 语言。
- 色弱与减少镜头晃动选项。

### 6.3 性能目标

首发最低目标建议：

- 推荐配置：1080p / 60 FPS。
- 最低配置：720p 或 900p / 稳定 30 FPS。
- 常规对局不出现明显长时间卡顿。
- 大规模坍塌允许短时降帧，但不能冻结输入。
- 进入关卡和重新开始必须有明确加载反馈。
- 后台或最小化时降低帧率和资源占用。

需要建立三档或四档画质预设，并保留自定义设置。

## 7. 核心玩法产品化

### 7.1 建造体验验收

- 新玩家五分钟内完成第一个 A 字结构。
- 预设名称、图示和实际旋转轴一致。
- 高度锁定后位置只由鼠标平面位置决定，不发生跳变。
- 幽灵牌清楚表示接触边、方向和米字辅助线。
- 非法放置必须给出明确原因。
- 撤销、重做、移动、删除和复制操作行为一致。
- 纸牌物理参数在不同帧率下保持可接受的一致性。

### 7.2 发射体验验收

- 输入过程清楚表达接触点、方向和力度。
- 玩家能够预测大致轨迹，但高手仍有提升空间。
- 炮台、弩、飞镖和投手在视觉与操作上明显不同。
- 发射失败可以看懂原因。
- 发射不会因帧率不同产生巨大力度差异。
- 关键命中提供镜头、音效、慢动作或回放反馈。

### 7.3 失败体验

避免“搭建三分钟，三秒钟不明原因全部消失”。

可使用：

- 分阶段目标。
- 有限抢修机会。
- 备用结构或局部蓝图。
- 倒塌原因回放。
- 关键支撑高亮。
- 第一回合降低秒杀概率。
- 比赛后显示命中点、速度和受力传播。

## 9. 联机架构

### 9.1 开发顺序

1. 单机对 AI。
2. 同设备本地双人。
3. 同规则下的好友在线测试。
4. 非排位休闲匹配。
5. 权威服务器排位。

在本地对战规则没有稳定前，不建设完整排位后台。

### 9.2 服务端权威原则

客户端只能提交操作意图，不能提交最终结果。

客户端可以提交：

- 选择的牌。
- 放置位置和旋转。
- 建造确认。
- 发射牌编号。
- 接触点。
- 发射方向。
- 蓄力时间或力度。

服务器负责：

- 验证玩家身份和游戏所有权。
- 验证当前是否轮到该玩家。
- 验证牌数、位置、角度和建造区域。
- 验证发射参数范围。
- 执行或验证权威物理模拟。
- 决定结构状态、目标状态和比赛胜负。
- 生成可审计的比赛事件日志。

### 9.3 推荐同步模型

对本项目推荐“回合指令同步 + 发射阶段权威模拟”：

1. 建造阶段同步离散的放置、移动和删除命令。
2. 服务端逐条验证命令并保存建筑状态。
3. 攻击阶段客户端提交一次完整发射输入。
4. 服务器运行无画面物理模拟或权威状态计算。
5. 服务端向双方广播关键状态快照。
6. 客户端使用插值和表现层播放结果。
7. 对局结束后保存输入日志和关键快照。

### 9.4 后端模块

- Steam 身份认证。
- 玩家资料。
- 房间和邀请。
- 匹配队列。
- 对局状态机。
- 权威物理房间。
- 断线重连。
- 排位与赛季。
- 库存和外观所有权。
- 比赛日志与回放。
- 举报与处罚。
- 运营配置。
- 指标和告警。

## 10. 反作弊方案

### 10.1 第一阶段

- 不信任客户端胜负结果。
- 所有操作验证回合和权限。
- 限制放置区域、数量、角度和频率。
- 限制发射力度、触点和输入频率。
- 使用 Steam Session Ticket 验证身份。
- 记录比赛指令。
- 检测重复包、乱序包和伪造请求。
- 对异常退出、超时和断线制定一致规则。

### 10.2 第二阶段

- 排位比赛由权威服务器运行。
- 建立异常力度和异常命中统计。
- 建立不可能操作检测。
- 比较客户端预测与服务器结果偏差。
- 为高排名和高举报玩家保留更完整录像。
- 提供玩家举报、人工复核和申诉流程。
- 封禁设备不是首选，优先处理可信账号与比赛资格。

### 10.3 第三阶段

只有在真实作弊规模出现后再评估：

- VAC 或 Steam Game Ban。
- 第三方反作弊。
- 客户端完整性检测。
- 更强的二进制保护。

反作弊不能只依赖扫描玩家电脑。最核心的防线始终是服务器不接受不合法结果。

## 11. 商业化结构

### 11.1 推荐模式

基础游戏采用买断制，提供完整可玩的核心内容。

推荐收入来源：

- 抢先体验销售。
- 1.0 正式版销售。
- 纯外观卡背。
- 桌面和竞技场主题。
- 击中与坍塌特效。
- 原声音乐。
- 支持者包。
- 大型玩法扩展。
- 后续主机移植。

### 11.2 禁止影响公平的付费内容

- 摩擦力加成。
- 发射力量加成。
- 更稳定的付费纸牌。
- 额外回合。
- 排位专属强力结构。
- 付费数值武器。
- 只能通过付费获得的战斗优势。

## 12. 测试与质量保障

### 12.1 自动化测试

- 放置预设旋转结果测试。
- 键位映射测试。
- 关卡目标判定测试。
- 存档读写和迁移测试。
- 回合状态机测试。
- 服务器输入验证测试。
- 断线和重连测试。
- 构建资源完整性测试。

物理结果不适合全部使用完全相等断言，可使用位置、角度和稳定时间的允许误差范围。

### 12.2 人工测试矩阵

- 不同 Windows 版本。
- Intel、AMD 和 NVIDIA 显卡。
- 集成显卡与独立显卡。
- 60 Hz、120 Hz 和 144 Hz。
- 不同 DPI 和显示缩放。
- 窗口、无边框和全屏。
- 中英文系统。
- 键鼠和手柄。
- 离线、弱网、高延迟和断线。

### 12.3 崩溃与诊断

- 捕获主进程和 Renderer 异常。
- 保存最近一次启动日志。
- 保存显卡、系统版本和游戏版本。
- 发生存档损坏时使用备份恢复。
- 上传诊断信息前获得玩家同意。
- 不在日志中记录密钥、访问令牌和个人敏感数据。

## 13. 数据指标

### 13.1 核心玩法验证

- 新玩家完成首个 A 字结构所需时间。
- 新玩家完成第一次有效发射所需时间。
- 教学关卡完成率。
- 首局完整完成率。
- 单局平均时长。
- 建造阶段和攻击阶段时间占比。
- 首回合直接结束比赛的比例。
- 对局结束后立即重赛率。

## 16. 是否迁移引擎的决策门槛

只有满足以下一项或多项，才正式评估 Unity、Godot 或其他方案：

- Cannon 无法满足服务器权威物理需求。
- Electron 在目标配置上长期无法达到性能要求。
- Electron 显著限制主机平台移植。
- 当前美术和动画管线无法扩展。
- WebGL 在大量纸牌坍塌时存在不可解决的稳定性问题。
- 团队已具备足以抵消重写成本的引擎经验。

迁移前必须制作同一小型场景进行数据对比，不能只凭“更像游戏”决定重写。

## 18. 最终原则

1. `.exe` 解决发行体验，不解决核心玩法。
2. 代码混淆提高逆向成本，不创造真正安全。
3. 敏感数据必须留在服务器。
4. 反作弊的第一原则是客户端不能决定结果。
5. 玩法规则稳定后再建设完整联机系统。
6. 抢先体验版本必须在发售当天就值得当前价格。
7. 商业化不能破坏物理竞技公平。
8. 第一目标不是建设所有系统，而是证明玩家愿意反复完成“建造—发射—坍塌”循环。

产品化成功的最终判断标准不是“它看起来不像网页”，而是：

> 玩家愿意安装、愿意付费、能够稳定完成比赛、相信比赛结果公平，并愿意再次游玩和分享自己的物理故事。
